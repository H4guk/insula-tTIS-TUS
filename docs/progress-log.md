## 2026-08-03 ★ 2週間のブロッカーを解決し Phase 1 dev を完走
この日だけで **工程5〜9 を作り切り、ペア1・ペア2 の両方を Run して TI 包絡まで到達**した。

**根本原因の特定（対照実験）**
- 方針①「GUI で最小 sim を焼いて差分を取る」を実行 → GUI で組んだ箱も空に見えたため一度は
  「Python 起因ではない」と結論したが、これは**誤診断**だった。
- 誤診断の正体は判定指標で、**`Voxel Scene Memory Consumption` は幾何の複雑さ（圧縮効率）の指標**であって
  中身の量ではない。`Voxel Log` でエンティティ単位を見ると GUI 製の箱は **15,625 ボクセルで正常に焼けていた**。
  → **判定は `Voxels:` の件数で行う**。
- そのうえで**同一プロジェクト・同一グリッド・同一 sim の中に GUI 製の箱と Python 製の箱を並べる**
  対照実験を行い、**GUI 製は焼かれ・Python 製は `not being considered`** を確認。
- 分岐を2択で潰した結果、**真因＝σ を割り当てたエンティティが `AutomaticVoxelerSettings` に
  登録されていないこと**と確定。`sim.AddMaterialSettings([e])` は材料しか紐付けないのに対し、
  **GUI のドラッグは Voxeler / Grid 設定にも自動登録していた**。修正は実質 `sim.Add(voxeler, [e])` の1行。
- これで **7/22 以降の全事象が1本で説明できる**: `... is not being considered` / ボクセルシーンが空 /
  `0 unknowns・0 Dirichlet points` / 全点 NaN / `no lossy dielectrics`。
  無罪が確定したのは Yoon-sun（ViP）・電極ジオメトリ・グリッド範囲・BC・材料DB・環境・バージョン。

**構成として確定したこと（当日の実測で覆った判断を含む）**
- **Grid 設定への登録は不要かつ有害** — 63個を `AutomaticGridSettings` に登録すると自動グリッドが
  エンティティ形状に合わせて細分し、`MaxStep` を 50mm にしても `Cell limit exceeded`。
  削除した瞬間に `125 x 121 x 134 = 2.027 MCells` で通った。刻みは
  **`GlobalGridSettings`（体5mm）＋ 頭部ブロックの `ManualGridSettings`（頭2mm）**で与える。
  副産物として **`GlobalGridSettings.Name` がセル数の表示そのもの**（失敗時 `Grid (Invalid)`）。
- **BC はソリッド本体に付ける（面BC は不可）** — `sim.AddBoundarySettings(face)` は面に恒久的な
  紐付けを作らず、**常に最後の1つだけが単一の無名コンポーネントに載る**ため電極対を駆動できない。
  → 7/30 の「面BC が正解」は撤回。
- **駆動電極には材料σを付けない** — σ と Dirichlet BC を同一ソリッドに載せると HDF5 の
  `attribute already exists` で Run が拒否される（7/30 の診断は正しかった）。失うものは無く、
  Dirichlet を付けた電極はどのみち `will be reassigned to PEC` で σ は使われない。
- **再実行前に `sim.ClearResults()` が要る** — 結果を持ったまま Run すると
  「材料σ＋BC の二重登録」と**同一メッセージ**で拒否される。区別は `sim.HasResults()`。
- **`Voxeler.log` は焼き終わったあとの `document.Save()` で書き出される** — `CreateVoxels()` は
  非同期で即座に戻る。「ログが出るまで待つ（保存しない）」実装だと永遠に現れず、
  この日 601 / 900 / 300 秒の空待ちを3回発生させた。

**成果物（工程5〜9 の4スクリプト）**
`assign_materials.py`（工程5 材料σ＋Voxeler 登録）→ `setup_boundary.py`（工程6 BC）→
`setup_grid.py`（工程7 グリッド→ボクセル）→ `run_simulation.py`（工程8 Run ＋ 工程9 検証）。

**実測値（Phase 1 dev の DoD）**
- グリッド: 両ペアとも `125 x 121 x 134 = 2.027 MCells` で **3軸とも完全一致**（`identical=True`）。
- ボクセル: レポート61件（組織59＋駆動電極2）・`not being considered` **0件**。
  焼けないのは `Commissura_anterior` / `Commissura_posterior` の2件のみ（数mm・頭部2mm では解像不可・prod で回収）。
- ソルバー: LF1 `564,753 unknowns / 7,120 Dirichlet`・LF2 `564,625 / 7,077`。
  `total dofs 2,075,220` と `NaN 数 1,499,146` は**両ペアで完全一致**＝同一ボクセルシーン上で解けている。
- E 場: **材料領域の非ゼロ有限率 99.98% / 99.97%**（`|E| max` 120.3 / 88.7 V/m）。

**判定基準の誤りを8件訂正**（実体ではなく判定側が壊れていたケース）
`Voxel Scene Memory Consumption` の意味／材料設定のキー名は `ms.Name`（DB の材料名）が入る／
`component.Name` には `  (Yoon-sun v3.1 Static)` の接尾辞が付く／`UpdateGrid()` は失敗しても例外を投げない／
finite 率は**全点ではなく材料領域**で見る（全点だと 26.03% が正常・`unused` と NaN 数の一致で裏を取る）／
仕様変更を全スクリプトのゲートに同期し損ねた／期待値63 は古く現構成では61／
`Wall Clock Time` は voxeler の内部計算時間であって実時間ではない。
共通する原因は「**期待値・指標の意味を実測で確かめずに固定した**」こと。
以後、**期待値は可能な限り実行時に sim から導出**し、検証コードは**集約値ではなく内訳を出力**させる。
